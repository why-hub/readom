# 08 · 改 `system.img` 里的 `build.prop`

这份文档只讲一件事：**在不重新打包 `system.img` 的前提下，怎么安全地增删 `build.prop` 里的属性。**

本项目的型号名（[05](05-model-name.md)）、ART 堆大小（[03](03-weread-heapsize.md)）、
EPDC 调试开关（[06](06-touch-display.md)）都是这么改的。踩过的坑也都在这里。

---

## 硬约束：文件大小必须一字不差

`build.prop` 在这台机器的 `system.img` 里是**定长 4719 字节**，位于
`83430 × 4096 + 58` 字节处。这个偏移被已有的工具（`patch-buildprop-heapsize.py`）依赖：

```python
FILE_OFFSET = 83430 * 4096 + 58
FILE_SIZE   = 4719
```

所以所有改动都是**等长字节替换**：加多少字节，就从注释里减多少字节。

为什么不干脆重打包镜像让它变大：

- `system.img` 是 ext4 文件系统镜像，改文件大小会动 inode、块位图、目录项，
  手工算这些等于重写一个 ext4 写入器；
- 长度一变，所有依赖固定偏移的工具全部失效；
- 这台机器没有 fastboot 逃生口，改坏了就得重新刷原厂固件（写分区，风险等级完全不同）。

---

## 坑一：尾部那段 NUL 填充会被 preinit 丢掉

镜像里 `build.prop` 真实文本只有 4661 字节，后面跟着 **58 字节的 `\0`** 凑满 4719。

看起来很理想——58 字节的空位，够塞两条属性。**但这是错的。**

设备上读到的 `/system/build.prop` 是 **4719 字节、尾部没有 NUL**：preinit 挂载时
会重写这个文件，把填充去掉。于是：

| 版本 | 属性位置 | 结果 |
|---|---|---|
| v27 | `full_every` 写在第 78 行（正文） | ✅ `getprop` 能读到 |
| v27 | `fast` 追加在文件末尾（填充区） | ❌ 被丢 |
| v28 | 两个属性都写进填充区 | ❌ 两个都被丢 |

更麻烦的是 v28 那次**症状很像别的问题**：镜像里 `fast` 明明在，设备上 `getprop` 却是空的。
判断依据是设备 `build.prop` 尾部 `od -c` 看不到 `\0`，而镜像里有——两个文件根本不是同一份内容。

**结论：属性只能写进正文区（4661 字节以内）。**

---

## 坑二：设备的 `build.prop` 和镜像的不是逐行对齐

设备上 132 行，开头是：

```
# begin build properties
# autogenerated by buildinfo.sh
```

镜像里 129 行，第 1 行直接是 `ro.build.id=OC…`。

preinit 会往头部插 3~4 行样板。所以**打补丁时用来定位的字符串必须在镜像里找，不能照设备的行号。**
第一版 v30 就是这么写废的：锚点用了 `# autogenerated by buildinfo.sh`，
那行在镜像里根本不存在（是 preinit 后来插的）。

---

## 做法：删两条无信息量的样板注释换空间

镜像里真实存在、且删掉不丢信息的样板行有这些（长度含 `#` 与空格）：

| 长度 | 内容 | 说明 |
|---|---|---|
| 38 | `# autogenerated by vendor_buildinfo.sh` | 构建脚本自动生成 |
| 29 | `# ADDITIONAL_BUILD_PROPERTIES` | 下面那批属性自己的小标题 |
| 74 | `# 12 MB less in /data. Given up: the boot image's address is no longer random.` | ART 注释，可压缩 |
| 29 | `# --no-watch-dog: see pw3.mk.` | 内容在下面 `dex2oat-flags` 行已体现 |

一段属性 `debug.pw3.epdc.a2=1` 是 22 字节，加上换行是 23。
所以替换时按「新内容 + 末尾空格补齐」来凑长度，例如：

```python
SUBS = [
    (b"# autogenerated by vendor_buildinfo.sh",  b"debug.pw3.epdc.settle_ms=150   "),
    (b"# ADDITIONAL_BUILD_PROPERTIES",           b"debug.pw3.epdc.a2=1           "),
]
```

替换后仍是 38 / 29 字节，整份文件长度不变。

> 注意行尾空格不影响 `getprop` 解析，但如果换成 `\0` 补齐就会被解析器当成行尾截断。

---

## 三步验证

改完不要只看「脚本说成功」，要按顺序验：

**1. 字节长度**

```python
blob = img[FILE_OFFSET : FILE_OFFSET + FILE_SIZE]
assert len(blob) == 4719
```

**2. 模拟 Android 的属性行解析**

按 `\n` 切行、遇 `\0` 视为结束，确认目标属性出现在某一行里、且该行以换行结尾
（最后一行没换行会被解析器丢掉，v27 的 `fast` 就是这么丢的）：

```python
text = blob.rstrip(b"\0")
lines = text.split(b"\n")
assert b"debug.pw3.epdc.fast=1" in lines
```

**3. 设备上 `getprop`**

```
adb shell getprop debug.pw3.epdc.fast        # 期望 1
adb shell grep -n epdc /system/build.prop     # 看行号是否落在正文区
```

只有第 3 步过了才算成功。前两步只能证明「写进了镜像」，不能证明「preinit 没把它丢掉」。

---

## 改完必须重 pin

`system.img` 的 SHA-256 被钉在 `pw3-preinit.conf` 里做一致性校验，**哈希一变就必须重 pin**，
否则启动时校验不过、直接回原厂系统（看起来像「改坏了」）。

顺序：

```
python3 tools/update-preinit-system-sha.py --image /mnt/g/android/system.img
bash tools/build-duet-launcher.sh
python3 tools/update-launcher-receipt.py build/launcher/Readom-Duet.sh build/launcher/build-result.json
python3 tools/verify-duet-launcher.py
cp build/launcher/Readom-Duet.sh /mnt/g/documents/Readom-Duet.sh
```

最后再核对一次三项哈希（镜像 / preinit pin / 部署到用户分区的 launcher）一致。
