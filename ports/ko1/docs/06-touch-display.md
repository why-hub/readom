# 06 · 触摸与刷新

## 结论先说

**输入链路是干净的，慢在显示刷新的波形选择。**

抓数据能证明一半：触摸每 16 ms 就来一帧、一帧都不丢；
而屏幕每帧要 235~292 ms，因为绝大多数时候跑的是 GL16 灰阶波形，
最快的 A2 波形**一次都没被用过**。

所以「不跟手」有三层开销叠加，都不是触摸驱动的问题：

| 层 | 实测 | 能不能改 |
|---|---|---|
| EPDC 波形选择 | 292 ms/帧，`a2=0`、`gl16` 占七到九成 | 有厂商调试属性，但只能在启动时读 |
| 每帧固定等待 | `settle_ms=350` | 同上 |
| 合成方式 | SwiftShader 软件 GLES，44 ms/帧 | 换硬件合成，工作量另一量级 |

## 触摸链路的数据

抓 120 条触摸事件，按 `SYN_REPORT` 分帧还原轨迹：

| 观察 | 实测 |
|---|---|
| 帧间隔 | 中位数 **16 ms**（约 62 Hz） |
| 连续拖动中的丢帧 | **没有**，相邻帧坐标连续 |
| 快速划动 | 208 ms 内从 (843, 27) 到 (771, 691)，每帧 `dy` 由 40 增大到 97，平滑加速 |
| 坐标范围 | Y 轴 27–1416 全屏覆盖，读数准确 |

帧率稳定、无跳点、无卡顿——从手指到内核到 Android 的路径上没有可优化的地方。

---

## 慢在波形：面板自己会报数

`dumpsys SurfaceFlinger` 里有一行厂商库统计出来的数据，是最直接的证据：

```
PW3 panel: presents=373  a2=0  du=22  gl16=146  gc16=26
           send_us_total=36.4s  prepare_us_total=12.7s
```

含义：

| 字段 | 含义 |
|---|---|
| `presents` | 提交给面板的帧数 |
| `a2` / `du` / `gl16` / `gc16` | 各波形使用次数（A2 最快、GL16 最慢且质量最好） |
| `send_us_total` | 累计送波形耗时 → 除以 `presents` 就是每帧成本 |
| `prepare_us_total` | 累计准备耗时（合成、拷贝） |

滑动 5 次后的实测增量：

| 指标 | 值 |
|---|---|
| 帧数 | 33 |
| `send_us` 增量 | 约 9.6 s → **292 ms/帧（3.4 fps）** |
| 波形分布 | `gl16` 24、`du` 4、`gc16` 5、**`a2` 0** |
| 准备耗时 | 44 ms/帧 |

也就是说：手指 16 ms 送一帧，屏幕 292 ms 画一帧，只来得及画 1/18。
而且**最快的那档波形根本没启用**——GL16 是为图片和照片准备的灰阶波形。

## 厂商库留了 11 个调试属性

`/vendor/lib/hw/gralloc.pw3.so` 里带着一批 `debug.pw3.epdc.*`：

```
debug.pw3.epdc.a2              真正控制 A2 的开关
debug.pw3.epdc.fast            另一条快速路径（不是 A2）
debug.pw3.epdc.full_every      每 N 帧插一次全刷，清残影
debug.pw3.epdc.settle_ms       每帧固定等待，默认 350
debug.pw3.epdc.clean
debug.pw3.epdc.contrast
debug.pw3.epdc.dither
debug.pw3.epdc.exact
debug.pw3.epdc.direct_percent  三个策略阈值，决定什么时候允许用快波形
debug.pw3.epdc.move_percent
debug.pw3.epdc.page_percent
```

启动日志印证了默认值：

```
PW3Gralloc: EPDC framebuffer open ready: ... settle_ms=350
```

> 一条排查教训：一开始只找到 3 个属性，是因为正则写成了 `[a-z._]`，
> 数字匹配不上，把 `a2` 截成了 `a`，在 `sort -u` 里去重时被吞掉。
> 正确写法：`grep -ao 'debug\.pw3\.epdc\.[a-z0-9_]*'`。

---

## 属性只在 SurfaceFlinger 启动时读一次

这是最关键的一条限制：

| 尝试 | 结果 |
|---|---|
| `setprop debug.pw3.epdc.settle_ms 150` 运行时改 | ❌ 无变化 |
| `setprop ctl.restart surfaceflinger` | ❌ SELinux 拒（production build 无法 root） |
| 熄屏 → 亮屏（面板重新 `open`） | ❌ 不重读，日志里没有新的 `open ready` |
| 写进 `build.prop`（启动时注入） | ✅ `getprop` 能读到 |

所以这类调优**只能走改 `system.img` 的路线**，方法见 [08](08-buildprop-editing.md)。

### 已验证的两个结果

| 版本 | 注入的属性 | 结果 |
|---|---|---|
| v29 | `fast=1`、`full_every=20` | 属性读到了，但 `a2` 仍是 0，连 `du` 也归 0，25 帧全 GL16 → **`fast` 不是 A2 开关** |
| v30 | 追加 `a2=1`、`settle_ms=150` | 已生成镜像 `6ade9ac0`，待部署验证 |

`fast` 这一条本身也是有价值的负面结论：库里有多个「快速」路径，
真正决定波形的是 `a2` 那个开关，而 `direct_percent` / `move_percent` / `page_percent`
是允许使用快波形的阈值——如果 `a2=1` 之后仍然是 0，下一步就是读这三个阈值。

## 上一版文档里判断错的地方

旧版写「用户态没有调节入口，要改善得动显示栈」，**只对了一半**：

- 「动显示栈」的直觉是对的——确实要改刷新策略；
- 但入口其实存在，只是要写进 `build.prop` 才能在启动时生效，而不是运行时 `setprop`。

## 现实预期

| 阶段 | 帧率 | 体感 |
|---|---|---|
| 现状（GL16 为主） | 3.4 fps | 手指滑完屏才动，明显滞后 |
| A2 生效（按波形时序估算） | 7–8 fps | 能跟上手指，仍有轻微拖影 |
| 手机级跟手 | 60 fps | 这块屏物理上做不到 |

即使 `a2=1` 生效也不会变成手机那种跟手：EPDC 每刷一帧都要扫全屏 1448 行，
A2 单帧的物理下限就在 120–150 ms 一带。**3.4 → 7~8 fps 是这块屏能拿到的全部空间。**

代价也要提前知道：A2 是黑白波形，文字滚动会跟手，但图片、漫画、封面会有明显残影。
`full_every=20` 就是用来每 20 帧插一次全刷清残影的，具体效果只能靠眼睛判断。
